# 기능 명세

서비스 규칙을 도메인별로 적은 문서입니다. 코드와 명세가 다르면 명세를 기준으로 판단합니다.

## 파일 구성

- `common.md`: 용어, 시간 기준, 상태 등 공통 규칙
- [`erd.md`](erd.md): 테이블 구조
- `{도메인}.md`: 도메인별 기능 명세 (예: [`auth.md`](auth.md))
- [`open-questions.md`](open-questions.md): 기획에 확인할 질문

## 기준 문서

- 동작은 기능 명세, 테이블 구조는 `erd.md`를 기준으로 합니다.
- 둘이 다르면 임의로 고르지 않고 `open-questions.md`에 올립니다.

## 작성 규칙

- 기능마다 `ROOM-01`처럼 ID를 붙이고, 시나리오는 `ROOM-01-1`처럼 이어서 붙입니다.
- 처리 규칙 1개에는 확인할 내용 1개만 적습니다.
- 규칙마다 근거를 붙입니다: `[정책서]`, `[PRD]`, `[WF 22]` (화면설계서 번호), `[구현 결정]` (백엔드가 정한 구현 방식)
- 정해지지 않은 정책은 `[미정]`과 질문 번호를 적습니다. (예: `[미정] Q-03`)
- 시나리오 ID는 테스트 이름에 그대로 씁니다. 메서드 이름에는 `-`를 쓸 수 없어 `_`로 바꿉니다. (예: `VOTE_04_2_정오에_마감한다`)

## 기능 양식

```markdown
## ROOM-01 기능 이름

상태: 미구현

### 기능 설명
이 기능이 하는 일 한두 줄

### 입력
- 받는 값

### 처리 규칙
1. 규칙 [정책서]
2. 규칙 [WF 22]

### 출력
- 돌려주는 값

### 예외
- 실패·경계 상황

### 제외 범위
- 이 기능에서 다루지 않는 것

### 완료 조건

**ROOM-01-1 시나리오 이름**
- Given 초기 상태
- When 동작
- Then 기대 결과
```

`상태`는 `미구현`, `구현됨`, `수정 필요` 중 하나로 적습니다. 구현된 기능의 규칙을 바꾸면 `수정 필요`로 바꾸고 다시 진행합니다. 계획서를 쓰는 기능이면 `/spec-plan`부터 진행합니다.
