## 명세 점검
- 상태 전이
  - 방어권: `보유 중`(`used_at` NULL) → `사용됨`(`used_at`, `used_round_id`). 되돌리지 않는다
  - 회차 결과: `PICKED` → `DEFENDED` (방어). 반대 방향은 없다. 차순위로 넘기지 않는다 (SHIELD-02 5번)
  - 지목된 사람의 처음 조회 시각: 결과 조회(RESULT-02) 또는 방어권 사용 때 비어 있으면 채운다 (SHIELD-02 3번)
  - 번뇌 완료 보상: 회차당 한 번 (장부 `BEONNOE`, 원인 `ROUND` 회차 ID)
- 동시성
  - 구매(SHIELD-01-4): 사용자 전체 잔액을 읽고 빼므로 사용자 행 락 안에서 확인하고 기록한다. 나가기 차감과 같은 사용자 락이다
  - 사용(SHIELD-02-9, 11): 방어권 하나로 두 방에서 동시에 쓰지 못하게 사용자 행 락을 먼저 잡고, 결과를 바꾸고 톡톡과 겹치지 않게 방 행 락을 잡는다. 순서는 방 만들기·입장·나가기와 같은 사용자 → 방
  - 같은 회차에 두 번 쓰지 않게 `UNIQUE (used_round_id)` (ERD)
  - 목탁 수행 완료: 장부의 `UNIQUE (user_id, reason, ref_type, ref_id)`로 한 번만 적립한다. 방어와 겹치지 않게 방 행 락 안에서 결과가 `PICKED`인지 확인한다
- 권한
  - 구매: 로그인한 사용자 (방과 무관)
  - 사용·목탁 수행 완료: 그 회차에 지목된 본인 (`DEFENSE_008`, 목탁은 `TAP_005`)
- 외부 연동 실패: 없음
- 금액
  - 구매: 잔액 100석 이상이면 -100석 (`PURCHASE`, 원인 `DEFENSE` 방어권 ID). 응답은 표시 잔액
  - 번뇌 완료 보상: +10석, 개인만. 방어하면 없다 (RICE-01 6·7번). 방 인원 2명 이상일 때만 (RICE-01 1번)
- 임시 결정 (2026-11-15, 기획 확인 중. `open-questions.md`는 기획 답이 오면 결정으로 바꾼다)
  - Q-76: `인증 안 함`으로 지목된 사람도 방어권을 쓸 수 있다
  - Q-77: 결과를 열지 않으면 방어 기회는 다음 투표가 열릴 때까지다. 그 뒤에는 처음 열어도 방어할 수 없다 (`DEFENSE_009`)
  - Q-93: 방어돼도 톡톡을 보낸 사람의 +5석은 유지한다 (회수하지 않음)
  - Q-92: 목탁 수행은 받은 톡톡(1번 이상, 재생 여부와 무관)이 있을 때만 하고, 다음 투표가 열리기 전까지 완료해야 보상을 준다. 받은 톡톡이 0번이면 수행·보상이 없다
- 제외 범위

  - 한 솥(POT-01): 번뇌 완료 보상은 원래 솥에 넣지 않는다
  - 목탁을 몇 번 쳤는지 서버에 저장 (화면에서 처리, 끝까지 쳤을 때만 완료를 보냄)

## 설계

### API 계약
- `POST /api/defense-tickets` (SHIELD-01): 응답 201 `{ "riceBalance" }`(표시 잔액). 에러 `STORE_001`(409, 잔액 부족)
- `POST /api/rounds/{roundId}/defenses` (SHIELD-02): 응답 201 데이터 없음. 확인 순서는 `api.md` 그대로 `ROUND_001` → `ROOM_002` → `RESULT_001` → 이미 방어함(성공) → `DEFENSE_008` → `DEFENSE_009` → `DEFENSE_002`
- `POST /api/rounds/{roundId}/moktak` (RESULT-03 9번, 새로 추가): 지목된 사람이 받은 톡톡만큼 목탁을 끝까지 두드렸을 때 한 번 보낸다. 요청 본문 없음. 응답 201 `{ "riceEarned" }`(10 또는 0)
  - 확인 순서: `ROUND_001` → `ROOM_002` → `TAP_005`(지목된 사람 아님) → `MOKTAK_001`(번뇌 보상이 없는 결과: `PICKED` 아님, 방어됨 포함) → 이미 완료(성공, `riceEarned` 0) → `MOKTAK_002`(받은 톡톡 없음) → `MOKTAK_003`(다음 투표가 열려 기한 지남)
- 결과 화면(RESULT-02): `defenseTicketCount`는 보유한 미사용 방어권 수, `canUseDefense`는 지목된 본인·`PICKED`·2분 안·다음 투표 전·1개 이상
- 새 에러 코드: `STORE_001`(409), `DEFENSE_002`(409), `DEFENSE_008`(403), `DEFENSE_009`(409), `MOKTAK_001`(409), `MOKTAK_002`(409), `MOKTAK_003`(409)

### 엔티티
- `DefenseTicket` (`defense_tickets`): user, purchasedAt, usedAt, usedRound. `UNIQUE (used_round_id)`, 인덱스 `(user_id, used_at)`
- `Round`: `defend()` (`PICKED` → `DEFENDED`)
- 장부: `RiceReason.PURCHASE`·`BEONNOE`, `RiceRefType.DEFENSE`·`ROUND`은 이미 있음

### 주요 결정
1. **구매 잔액 확인**: 사용자 행 락 안에서 장부 합계를 읽고 100석 이상이면 -100석을 기록한다. 다른 방의 적립·회수는 잔액을 읽지 않고 기록만 해서 막지 않는다 (나가기 차감과 같은 판단)
2. **사용 락 순서**: 사용자 행 → 방 행. 방 ID는 회차 ID로 먼저 구하고, 락 뒤에 회차를 READ COMMITTED로 읽는다 (VOTE-03·톡톡과 같은 이유)
3. **방어 기한**: 처음 조회 시각 + 2분 안이고, 다음 투표가 열리지 않았어야 한다 (Q-77). 처음 조회 시각이 비어 있으면 이 요청 시각으로 채운다 (SHIELD-02 3번)
4. **소모할 방어권**: 보유 중인 것 중 가장 먼저 산 것
5. **목탁 완료는 화면이 보낸다**: 몇 번 쳤는지는 서버가 확인하지 않는다. 받은 톡톡이 1번 이상 있는지만 본다. 중간에 포기하면 화면이 보내지 않는다
