# RESULT-03 이마 톡톡 5시간과 한 번에 전달

## 범위
- 구현 기능: RESULT-03, RESULT-02, RICE-01
- 참고 기능: SHIELD-02, VOTE-04, VOTE-05, ROOM-02

기획 답변(2026-11-15)을 반영합니다.
- 톡톡은 투표 마감 후 5시간 동안 보낼 수 있다. 예: 15:00 자동 마감이면 20:00까지.
- 받은 톡톡은 5시간이 지나 톡톡이 마감되면 지목된 사람에게 한 번에 전달한다.
- 목탁 수행은 전달된 뒤부터 다음 투표가 열리기 전까지 투표 탭에서 한다.
- Q-92 확정: 받은 톡톡이 0번이면 번뇌 완료 보상이 없다.

RESULT-02·03과 RICE-01은 한 솥, 리액션 등 다른 이유로 계속 `미구현`입니다. 이번에는 상태를 바꾸지 않습니다.

## 명세 점검
- 상태 전이: 새 상태 컬럼은 없습니다. "톡톡 중"과 "전달됨"은 `rounds.vote_closed_at + 5시간`과 지금 시각을 비교해 정합니다. 전달 시각에 도는 배치는 없습니다.
- 동시성:
  - 톡톡 전송은 지금처럼 방 행 락 안에서 결과(`PICKED`, `DEFENDED`)를 확인합니다. 방어와 엇갈리지 않게 하기 위해서입니다.
  - 목탁 수행은 전달 뒤에만 할 수 있습니다. 그 시점에는 톡톡이 더 오지 않아 받은 합계가 바뀌지 않습니다. 그래서 "수행 중에 톡톡이 더 오는 경우"(MOKTAK_004 재시도 안내)가 없어집니다.
- 권한: 바뀌지 않습니다. 보내기는 지목된 사람을 뺀 방 멤버, 받은 톡톡 조회와 목탁 수행은 지목된 본인만 할 수 있습니다.
- 외부 연동 실패: 없습니다. 전달 알림 푸시는 정책에 없어 만들지 않습니다.
- 제외 범위:
  - 톡톡과 목탁 수행 연출(화면)
  - 앱 진입 이벤트(ROOM-02 `entry`, 팀원 담당). 진입 이벤트는 유지하고, 미재생 톡톡은 전달 뒤에만 센다는 점을 팀원에게 전달합니다 (주요 결정 5)
  - 투표 탭 화면 연결(화면에서 처리, 주요 결정 3)

## 설계

### API 계약
- `POST /api/rounds/{roundId}/taps`: 요청과 응답은 바뀌지 않습니다. `TAP_004`는 "투표 마감 후 5시간이 지남"이라는 뜻이 됩니다.
- `GET /api/rounds/{roundId}/taps/received`
  - 응답: `{ isDelivered, deliveredAt, totalCount, isMoktakDone, taps[] }`
  - 전달 전(`isDelivered=false`)에는 `taps`가 빈 배열이고 `totalCount`는 0입니다.
  - 전달 뒤에는 건너뛰기(0번)를 뺀 받은 톡톡 전체가 오고, 재생 여부와 상관없습니다. `totalCount`는 목탁 수행에서 두드려야 하는 횟수입니다.
  - 방어된 회차는 지금처럼 빈 배열이고, `totalCount`는 0입니다.
  - 에러: 지금과 같습니다 (`ROUND_001`, `ROOM_002`, `TAP_005`).
- `PUT /api/rounds/{roundId}/taps/received/played`: 바꾸지 않습니다. 진입 이벤트(ROOM-02)에서 한 번 띄운 뒤 다시 띄우지 않으려고 씁니다.
- `POST /api/rounds/{roundId}/moktak`: 요청과 응답은 같습니다. 새 에러 `MOKTAK_005` (409, 톡톡이 아직 전달되지 않음)를 추가합니다.
  - 확인 순서: `ROUND_001` → `ROOM_002` → `TAP_005` → `MOKTAK_001` → 이미 완료(`riceEarned` 0) → `MOKTAK_005` → `MOKTAK_002` → `MOKTAK_003` → `MOKTAK_004`
- `GET /api/rounds/{roundId}/result`: 필드는 바뀌지 않습니다. `isTapExpired`와 `canTap`이 5시간 기준이 됩니다.

### 엔티티
- `Round.getTapClosesAt()`: `voteClosedAt + 5시간`입니다. 컬럼은 추가하지 않습니다.
- `Tap.playedAt`은 그대로 둡니다. 조회 필터에서만 빠집니다.

### 주요 결정
1. **경계 시각** [구현 결정]
   - 톡톡은 `tapClosesAt` 전까지 보낼 수 있습니다. 예: 19:59:59까지.
   - `tapClosesAt`부터 전달된 것으로 봅니다. 예: 20:00:00부터 받은 톡톡 조회와 목탁 수행이 가능합니다.
   - 같은 시각을 기준으로 둘이 겹치지 않게 했습니다.
2. **"한 번에 전달"은 시각으로 구분합니다** [구현 결정]
   - 전달 배치나 전달 기록 컬럼 없이, 조회 시각이 `tapClosesAt` 이후면 전달된 것으로 봅니다.
   - 서버가 꺼져 있어도 전달이 밀리지 않습니다.
3. **투표 탭 상태(VOTE-05)는 그대로 둡니다** [구현 결정]
   - 결과를 본 뒤 다음 투표 전까지는 `결과 확인 후` 상태이고, 응답에 최근 발표 회차 ID가 옵니다.
   - 화면은 그 회차의 결과 화면(톡톡 가능 여부)과 받은 톡톡 조회(전달 여부, 목탁 수행 완료 여부)로 톡톡과 목탁 수행 화면을 고릅니다.
   - 투표 탭에 어떤 화면을 연결할지는 화면에서 정합니다 (사람 확인, 2026-11-15).
4. **목탁 수행 완료 여부를 받은 톡톡 조회에 담습니다** [구현 결정]
   - 수행이 다음 투표 전까지 여러 번 들어올 수 있는 화면이 됐습니다. 그래서 지난 PR에서 미뤘던 `totalCount`와 `isMoktakDone`이 필요해졌습니다.
   - 결과 화면에는 넣지 않습니다.
5. **앱 진입 이벤트는 유지합니다** (사람 확인, 2026-11-15)
   - 전달된 뒤 지목된 사람이 처음 앱에 들어오면 받은 톡톡(목탁 수행) 화면으로 바로 갑니다.
   - 그래서 진입 이벤트의 미재생 톡톡(ROOM-02 `entry.unplayedTapRoundId`)은 전달 뒤(`tapClosesAt` 이후)에만 셉니다. ROOM-02는 팀원 담당이라 이 조건을 전달합니다.
